# LobeHub Migration To-Do

The working checklist behind the
[LobeHub Packages Migration Plan](./lobe-packages-migration-plan). The plan says
*what* the target architecture is; this page tracks *where each piece stands* and
what the next concrete step is. Every item names the file that owns it, so a run
can pick one up without re-deriving the seam.

The map of what already connects is
[LobeHub Integrations Reference](./lobehub-integrations).

## Phase 1 — Chat mode powered by the engine

### 1.1 Stand up staging ⬜

Needs Cloudflare account access, so it cannot be done from a code-only run.

1. `cd packages-lobe && pnpm install && bun run build:worker`
2. Create the Hyperdrive config and paste the id into `wrangler.jsonc`
   (or set `DATABASE_URL` to a Neon URL and keep `DATABASE_DRIVER=neon`).
3. `bun run db:migrate` (Postgres, 157 migrations) and `bun run cf:d1:migrate` (D1).
4. `bun run cf:deploy`, then smoke `/api/health`,
   `/trpc/lambda/config.getGlobalConfig`, `/signin`.

Until then, `bun run cf:dev` (local wrangler, dummy secrets, local D1/KV) is the
only end-to-end check available.

### 1.2 Search tool = `search-web-api` ✅

Done: `apps/server/src/services/search/impls/qwksearch/` implements
`SearchServiceImpl` against Worker A's `GET /api/agent/search`; registered as
`SearchImplType.QwkSearch`; enabled via `SEARCH_PROVIDERS=qwksearch` in
`wrangler.jsonc`. Category normalization, 3-way fan-out, URL-merge and failure
mapping are covered by `impls/qwksearch/index.test.ts` (20 cases). The contract
is written up in §F5 of the integrations reference.

Follow-ups that are deliberately *not* in that change:

- ✅ **Extend the tool manifest's category enum.** Done the second way the
  option offered: `packages/builtin-tool-web-browsing/src/searchCategories.ts`
  (new file) resolves the enum at module evaluation and widens it *only* when
  `SEARCH_PROVIDERS` names `qwksearch` and nothing else, so no other backend is
  ever asked for a category it cannot serve. `manifest.ts` gains an import and
  swaps the literal for `resolveSearchCategories()`; the package index gains one
  export line. Those three lines are the whole upstream edit.

  The widening is to **ten**, not thirteen — the fan-out endpoint takes SearXNG
  spellings, and QwkSearch's 13-name registry aliases onto those ten in
  `normalizeCategories`. The five the model gains are `files`, `it`, `map`,
  `music` and `social+media`. Drift between the advertised list and the accepted
  one now fails a test in `impls/qwksearch/index.test.ts` (27 cases, was 20).

  Two caveats worth knowing: the enum is fixed at module evaluation, which is
  safe on the Worker only because `worker/cf/globals.ts` mirrors vars onto
  `process.env` before anything else evaluates; and in the SPA there is no
  `process`, so the client-side copy of the manifest always reports LobeHub's
  five. Nothing on the client reads the enum today.
- ⬜ **Service binding instead of HTTPS.** `QwkSearchImpl` calls Worker A over
  the public internet. Once both Workers deploy together, a Cloudflare service
  binding removes a hop and the need for `QWKSEARCH_API_KEY`.
- ⬜ **Ranking parity.** The fan-out's scores come from `search-web-api`;
  `domain-rank` (favicons, domain authority) is not consulted on the engine side.
  Decide whether that belongs in the endpoint or the impl.

### 1.3 Extraction chain, tier 0 = the QwkSearch article extractor ✅

Done. `worker/qwksearch/extractQwkSearch.ts` adapts `extract-webpage`, and
`tiersForUrl` in `worker/qwksearch/extract.ts` routes each URL kind to its chain.
One `extractContent` call covered all three sub-items, because the extractor
branches on the URL itself.

1. ✅ **Tier 0 = `extract-webpage`**, ahead of the scraper, bringing citation
   extraction (`author_cite`, `author_short`, `author_type`, date, source) that
   the readability path could not produce. It writes through the same D1
   `articleCache`, so nothing about the panel's storage changed.
2. ✅ **YouTube** is its own `UrlKind`, extracted as a transcript through
   `extract-youtube`, instead of being rejected in `VIDEO_PATTERNS`. Only
   Vimeo/Dailymotion/Twitch — hosts with no transcript route — still get the
   "not an article" stub.
3. ✅ **PDF and arXiv** are their own `UrlKind`, routed to `extract-pdf`
   through the extractor's PDF branch. `.pdf` (with or without a query string)
   and `arxiv.org/pdf/` match; `arxiv.org/abs/` stays on the article path
   because those pages are HTML.
4. ✅ Every tier still returns `{ error }` rather than throwing — including a
   failed *module load*, which is why the package is behind an injectable lazy
   loader. Tests inject a fake module, so they never load the real extractor.

Two things worth knowing before building on this:

- **`linkedom` is no longer shimmed** in `vite.worker.config.ts`. It was stubbed
  to throw because LobeHub only reached it from the dev-server template
  rewriter, but `extract-webpage` parses every page with it and it runs fine on
  workerd. `worker/shims/linkedom.ts` is gone. The Worker bundle went from
  **7.39 MB to 7.93 MB gzipped** against Cloudflare's 10 MB limit — see 5.4.
- **The scraper tier got better too.** When tier 0 fails but Puppeteer gets past
  the bot check, the rendered HTML now runs through the same citation extraction
  (`articleFromRenderedHtml`) instead of discarding the byline. It falls back to
  LobeHub readability if that yields nothing.

Follow-ups that are deliberately *not* in that change:

- ✅ **Per-user extraction settings — resolution layer.** Done in 1.5 below;
  what remains is the UI that writes to it (2.2).
- ✅ **PDF OCR modes.** `PDF_PROCESSOR` /
  `PDF_PROCESSOR_URL` reach `extract-pdf` through 1.5.
- ⬜ **Bundle budget in CI** (5.4) matters more now that the margin is ~2 MB.

#### ✅ Resolved: the second chain in `extract.ts` is deleted

`extract.ts` used to define **two** tier chains, and only one of them ran:

| | `tiersForUrl` (live) | `defaultTiersFor` (deleted) |
|---|---|---|
| article | `qwksearch → scraper → tavily → crawler` | `scraper → tavily → crawler` |
| youtube | `qwksearch` | `extractViaYouTube → scraper → tavily → crawler` |
| pdf | `qwksearch` | `extractViaPdf → tavily` |

The decision was framed as adopt-or-delete. It turned out not to be a judgement
call at all, because **the unwired chain could not have run if it had been
wired**:

- `extractViaYouTube` calls `youTubeVideoId(url)` and `extractViaPdf` calls
  `pdfUrlFor(url)`. Neither identifier is defined in `extract.ts`, imported into
  it, or present anywhere else in the repository — `tsc` reports both as
  `TS2304: Cannot find name`. Every YouTube and PDF extraction through that
  chain would have thrown `ReferenceError` on its first line, been caught by
  `extractArticle`'s per-tier `try`, and fallen through as a tier failure.
- Both tiers also returned `via: 'youtube'` and `via: 'pdf'`, which are not
  members of the `ExtractedArticle['via']` union they are typed against
  (`TS2345`).

So adopting it would have been a regression twice over: for `article` URLs it
drops tier 0 and with it the citation extraction §1.3 exists to deliver, and for
the two media kinds it leads with a tier that cannot execute. Deleted, along
with `WEB_TIERS`, the two tiers and their support cast (`TranscriptFetcher`,
`YouTubeConfig`, `loadTranscriptFetcher`, `transcriptToParagraphs`,
`fetchYouTubeMetadata`, `PdfConverter`, `PdfConfig`, `loadPdfConverter`), the
two helpers that were dead for the same reason (`loadCiteExtractor`,
`articleViaCiteExtractor`, plus the `HtmlCiteExtractor` type and module-level
`citeExtractor` cache they shared), and the three helpers left unreferenced once
those went (`articleFromExtractedHtml`, `markdownOf`, `textOf`). 935 lines down
to 619; no behavior change, because none of it was reachable.

Nothing is lost by the deletion. The knobs the unwired tiers read are the ones
§1.5 already routes through tier 0 — `extract-webpage` branches on the URL
itself and calls `extract-youtube` and `extract-pdf` internally, with
`languages` and `PDF_PROCESSOR` / `PDF_PROCESSOR_URL` bound from the resolved
settings. `extractViaPdf`'s own `process.env.PDF_PROCESSOR_URL` read was in fact
the last direct `process.env` read in a tier, which is exactly what §1.5 set out
to remove.

§F2 of the integrations reference already described the live chain, so it needed
no rewrite — only a line recording that it is now the only one.

**Why it survived so long, and what now catches it:** nothing type-checks
`worker/`. The repo-wide `bun run type-check` includes it, but OOMs before
finishing (see below), and no CI job installs `packages-lobe` at all. Two
undefined identifiers sat in a request-path module from the day they were
written. `bun run type-check:worker` is the narrow check that closes that gap —
see §5.5.

### 1.5 Extraction settings resolution ✅

The extraction chain no longer hard-codes its knobs.
`worker/qwksearch/extractSettings.ts` owns one `ExtractionSettings` value, and
folds it out of three layers — shipped defaults, then Worker env, then
per-request overrides — validating every value on the way in. `tiersForUrl`
binds the resolved settings into each tier, so a tier no longer reaches for
`process.env` itself.

| Setting | Env var | Reaches |
|---|---|---|
| Citation style (`apa`/`mla`/`chicago`) | `QWKSEARCH_CITATION_STYLE` | `buildCite`, every tier |
| Transcript languages | `QWKSEARCH_EXTRACT_LANGUAGES` | `extract-youtube` via `languages` |
| Extractor timeout | `QWKSEARCH_EXTRACT_TIMEOUT` | `extract-webpage` `timeout` |
| Enabled tiers, in order | `QWKSEARCH_EXTRACT_TIERS` | `tiersForUrl` |
| Render backend + budget | `SCRAPER_URL`, `SCRAPER_API_KEY`, `QWKSEARCH_SCRAPER_DEADLINE_MS` | the Puppeteer tier |
| PDF OCR mode + endpoint | `PDF_PROCESSOR`, `PDF_PROCESSOR_URL` | `extract-pdf` via `processor` |
| Outbound proxy | `QWKSEARCH_EXTRACT_PROXY` | `extract-webpage` `proxy` |
| Third-party reader fallback | `QWKSEARCH_EXTRACT_THIRD_PARTY_BACKUP` | `extract-webpage` |

Three things worth knowing before building the pane on top of it:

- **The client layer is deliberately narrower than the user layer.**
  `GET /api/doc/article` honours `?cite=` and `?lang=` and nothing else. Every
  other setting either names a host the Worker would then send a bearer token to
  (`scraperUrl`, `pdfProcessorUrl`, `proxy`) or buys the caller compute
  (`pdfProcessor=docling` OCRs every page). `ClientExtractionOverrides` is typed
  to exclude them and `parseClientExtractionOverrides` never reads them.
- **Citation style survives the cache.** `articleCache` is keyed by URL and holds
  one `cite` string, so a non-APA request re-renders the citation from the cached
  fields rather than fragmenting the cache per style. APA keeps the stored
  string, which came out of the extractor's 90k-name database and beats anything
  the fallback builder assembles from columns.
- **An empty tier list is a real outcome.** `QWKSEARCH_EXTRACT_TIERS=scraper`
  leaves a PDF URL with no viable tier, and the caller gets the "no extraction
  tier configured" error rather than a tier the operator switched off.

Follow-ups:

- ✅ **The user layer now has storage and an API.** See 1.6.
- ⬜ **MLA/Chicago only reach the fallback builder's fields.** The extractor's
  own citation is APA, so a non-APA style is rebuilt from `author_cite`, `title`,
  `source` and `date` — correct, but it loses the extractor's author-type
  handling (organizations, two-author, more-than-two). Teaching
  `extract-webpage` the other styles is the real fix.

### 1.6 Extraction preferences: the user layer ✅

1.5 defined a user layer and gave it nowhere to live —
`UserExtractionOverrides` was a type `resolveExtractionSettings` accepted and
nothing ever produced. It now has storage, an API and a caller:

- `worker/qwksearch/extractionPreferences.ts` — load / save / clear one user's
  overrides, and `userExtractionOverridesForRequest(headers)` for the article
  route. Every read is validated again on the way out and never throws; a
  failure resolves to `{}` and the caller falls back to the operator's config.
- `worker/routes/qwksearch/extractionSettings.ts` —
  `GET`/`PUT`/`DELETE /api/doc/extraction-settings`, sign-in required, returning
  `{ overrides, effective, options }`.
- `extraction_settings` on D1 (`migrations/d1/0002_extraction_settings.sql`,
  idempotent like 0001; both files run from `bun run cf:d1:migrate`).
- `/api/doc/article` folds the layer in between env and query, so precedence is
  now **default → env → user → `?cite=`/`?lang=`**. A request with no `cookie`
  header skips the session lookup, so the anonymous path is unchanged.

The full contract is §F2b of the integrations reference.

**Correction to the plan.** 2.2 below used to say the Extraction pane needed
"nothing further server-side". That was wrong: the resolver took a user layer,
but no code path produced one, so a pane writing to
`src/store/user/slices/settings/` would have changed nothing about an
extraction. That gap is what 1.6 closes.

**Deliberate deviation.** The plan said to persist through LobeHub's user
settings store. The overrides are on D1 instead, keyed by the same LobeHub user
id as favorites and documents. Reading Postgres `user_settings` from a Hono
Worker route would couple the extraction chain to Hyperdrive for a six-field
blob, and adding a namespace to it means an upstream type edit plus a Postgres
migration — the opposite of the "keep changes additive" rule below. Phase 2's
"one system of record" is about the settings *surface*, and there is still
exactly one: the pane. If the panes later consolidate onto the LobeHub store,
this route is the migration's read side.

Follow-ups:

- ✅ **The client consumer landed** — 1.7 below.
- ✅ **`languages` is capped at five and `tiers` at the four known ids**; the
  pane reads both bounds out of `options` and never repeats them.

### 1.7 Extraction settings pane ✅ (#393)

2.2's Extraction half, shipped. `/settings/extraction` is a form over the one
JSON document 1.6 serves, and the first QwkSearch surface to live *inside*
LobeHub's settings shell rather than beside it. The full contract is §F2c of the
integrations reference.

```
src/features/Settings/extraction/
  index.tsx           SettingHeader + the form
  api.ts              GET/PUT/DELETE, and the response types
  formState.ts        form values ⇄ UserExtractionOverrides (pure, no React)
  features/ExtractionForm.tsx
```

Three things worth knowing before touching it:

- **An unset field is not a value.** `normalizeOverrides` drops `undefined`, so
  a field the user has not touched must be *absent* from the PUT body — not
  `null`, not `''`, and not the value that happens to be in force. Every input
  therefore has an explicit inherit state (`INHERIT` for the enums, an empty
  list, `null` for the timeout) and `overridesFromFormValues` omits those keys.
  This is why the third-party-fallback control is a three-way select rather than
  a `Switch`: `false` pins the user to off, unset follows the operator, and a
  switch cannot say both.
- **The inputs seed from `overrides`, never from `effective`.** Seeding from
  what is in force would turn every inherited field into an explicit override
  the moment the user saved anything, silently pinning them to today's server
  config. `effective` appears only as the hint under each input and as the
  timeout's placeholder.
- **The pane renders the response, not what it sent.** `PUT` trims — a sixth
  language, an unknown tier, a 99s timeout clamped to 60 — and the response is
  the authority.

`api.ts` restates the Worker's types instead of importing them, because `src/`
bundles for the browser and `worker/` for workerd. **`contract.test.ts` is the
drift guard**: it imports the real `extractSettings.ts`, rebuilds the exact
document the route returns, and runs a load → edit → save cycle back through
`normalizeOverrides`. An enum member or override field added on the server and
not in `api.ts` fails it.

Upstream edits are five registration points and no logic — the `SettingsTabs`
enum, both `componentMap`s, the sidebar item in `useCategory.tsx`, and the
compact-header title map in `SettingsContent.tsx`. No route file: `/settings/:tab`
already dispatches by enum value.

Follow-ups:

- ✅ **`languages` has a language picker.** Closed in 1.11 with the search
  pane's `language`, which had the same bug. It turned out to be worse than
  "a typo silently disappears": the field could not be filled in at all, because
  base-ui's `Select` never creates a value outside its `options` and this one was
  given none. See 1.11 and §F5d.
- ✅ **`tiers` is drag-to-reorder.** Closed in 1.11 with the search pane's
  `categories`, which had the same bug.
- ✅ **A 401 now prompts to sign in.** Closed in 1.10, which hit the same bug in
  its own pane: both forms recognise the 401 their API error already carried and
  say `*.error.loginRequired` instead of printing the status text, on load and on
  save alike.

### 1.8 Search settings resolution ✅

The search-side mirror of 1.5, and the first of the three steps the Search &
Sources pane needs. `QwkSearchImpl` no longer reads `process.env` itself or
hard-codes its knobs:
`apps/server/src/services/search/impls/qwksearch/searchSettings.ts` owns one
`SearchSettings` value and folds it out of three layers — shipped defaults, then
Worker env, then the signed-in user's preferences, then this tool call's own
arguments — validating every value on the way in. `index.ts` is left turning the
resolved value into HTTP.

| Setting | Env var | Reaches |
|---|---|---|
| Endpoint + bearer token | `QWKSEARCH_SEARCH_URL`, `QWKSEARCH_API_KEY` | the request URL and its `Authorization` header |
| Default categories | `QWKSEARCH_SEARCH_CATEGORIES` | `cat`, one request per category |
| Fan-out bound | `QWKSEARCH_SEARCH_MAX_CATEGORIES` | how many of them run (3 by default, up to 10) |
| Result language | `QWKSEARCH_SEARCH_LANGUAGE` | `lang` — **newly sent**; the endpoint already defaulted to `en-US` |
| Default recency | `QWKSEARCH_SEARCH_TIME_RANGE` | `recency`, when the call names none |
| Safe search | `QWKSEARCH_SEARCH_SAFE` | `safesearch` — newly sent |
| Public SearXNG fallback | `QWKSEARCH_SEARCH_PUBLIC_INSTANCES` | `publicInstances` — newly sent |
| Result cap | `QWKSEARCH_SEARCH_RESULT_LIMIT` | applied after the URL merge |

Four things worth knowing before building the pane on top of it:

- **It lives beside its consumer, not under `worker/`.** `extractSettings.ts`
  sits in `worker/qwksearch/` because the extraction chain does. The search impl
  does not: it is `@/server/*` code. The dependency runs worker → `@/server/*`
  and never back, so a future `/api/doc/search-settings` route can import this,
  while the reverse placement would not have worked.
- **The request layer is narrower than the user layer.** The tool call's
  arguments are written by the model, so they may narrow only `categories` and
  `timeRange` — the two fields the manifest offers it. `maxCategories` is
  withheld from it deliberately: it bounds how many upstream requests one query
  costs, which is the operator's budget and not a generated argument's to raise.
  `searchEngines` is still never read at all.
- **The cap is applied once, at the end.** The category list can arrive from the
  request layer while `maxCategories` comes from the user layer, so each
  normalizer returns the full validated list and `resolveSearchSettings`
  truncates after every layer has resolved.
- **Three query parameters the endpoint always accepted are now actually sent.**
  `lang`, `safesearch` and `publicInstances` were in
  `research-agent-ui/src/api/handlers/search.ts` the whole time and the impl
  never used them. Only `lang` changes the default request, and it sends the
  value the endpoint already assumed.

Follow-ups:

- ✅ **The user layer has storage** — 1.9 below.
- ⬜ **`searchSettingsForClient` has no client**, the same gap 1.6 left before
  1.7 closed it. `GET /api/doc/search-settings` serves it now; the pane is 1.10.

### 1.9 Search preferences: the user layer ✅

The search-side mirror of 1.6, and the second of the three steps the Search &
Sources pane needs. 1.8 gave `resolveSearchSettings` a user layer with no
storage; this is the storage, the route that writes it, and the wiring that
carries it to the fan-out.

| Piece | File |
|---|---|
| `search_settings` table + load/save/clear | `apps/server/src/services/search/impls/qwksearch/searchPreferences.ts` |
| D1 migration (idempotent, like 0001–0002) | `migrations/d1/0003_search_settings.sql` |
| `GET`/`PUT`/`DELETE /api/doc/search-settings` | `worker/routes/qwksearch/searchSettings.ts` |
| Table listed beside its siblings | `worker/qwksearch/schema.ts` (re-export) |

**The open question 1.8 left — how the user id reaches the impl — is answered by
threading it, not by a per-request factory.** `webBrowsingRuntime`'s factory
already receives a `ToolExecutionContext` carrying `userId`; it now passes it to
`new SearchService({ userId })`, which forwards it through
`createSearchServiceImpl(type, options)` to `new QwkSearchImpl({ userId })`. Four
one-line changes in a straight line, and no lifecycle change: the service is
still built per tool execution and still holds its impls for its own lifetime.
The rejected alternative — giving `SearchService` a per-request impl factory —
would have rebuilt every provider on every query to serve one of twelve.

Three decisions are worth knowing before building the pane:

- **The storage lives under `@/server/*`, not `worker/`, and the schema file
  re-exports it.** This is the one place the two features could not be twins.
  Extraction's preferences sit in `worker/qwksearch/` because only Worker routes
  read them; search preferences are read by `QwkSearchImpl` too, which is
  `@/server/*` code, and the dependency runs worker → `@/server/*` and never
  back. Only the `@/server/*` placement serves both, so `worker/qwksearch/schema.ts`
  re-exports the table rather than declaring it — the table still has exactly one
  definition and still appears beside its siblings. The D1 handle comes from
  `@/database/core/cloudflare`, the bridge the database package already uses to
  reach the bindings, so nothing imports `worker/` backwards. Cost: a second thin
  drizzle wrapper over the same `DB` binding, which is a pointer, not a pool.
- **The row is read once per impl, not once per query.** `overridesFor()` memoizes
  the *promise*, so a turn that fans out several searches pays one D1 read and
  concurrent queries collapse onto it. An impl is built per tool execution, so
  "once per impl" is once per conversation turn — there is no staleness window to
  invalidate.
- **A preferences outage degrades, it does not fail.** `loadUserSearchOverrides`
  resolves to `{}` on any read error and when there is no D1 binding at all, so a
  Node dev server, a non-Cloudflare deployment and a D1 outage all search on the
  operator's configuration. `overridesFor()` catches too, so an injected loader
  cannot break that guarantee and a rejected promise is never what the memo
  caches. Writes are the opposite and propagate, because the pane has to be able
  to say a preference was not saved.

The endpoint and the API key are excluded from the user layer at the type level
and the route proves it at runtime: `PUT`ing an `apiKey` or `endpoint` stores
neither, and `GET` reduces both to presence flags under `effective.configured`.
`PUT` returns what was actually stored, so a value that failed validation is
visible to the pane rather than silently dropped.

Verified by 31 new tests — 18 on the storage module and 13 on the route, both
running against the real resolver with only D1 and the session faked.

Follow-ups:

- ⬜ **`bun run cf:d1:migrate` must run before the route is useful.** Both migrate
  scripts in `package.json` name their files one by one and now include 0003; the
  table does not exist on `qwksearch-new` until someone with Cloudflare
  credentials runs it. Until then `GET` answers from defaults-under-env and `PUT`
  returns a 500.
- ⬜ **Not seen against a real D1.** No Cloudflare credentials here, so the
  drizzle calls are verified against a fake that reproduces the three chains the
  module uses, and never against SQLite.

### 1.10 Search & Sources settings pane ✅

1.7's equivalent, shipped, and the last of the three steps. `/settings/search` is
a form over the one JSON document 1.9 serves, built to 1.7's five-file shape and
registered at 1.7's same five points. The full contract is §F5c of the
integrations reference. **This closes 2.2** — both panes it asked for now exist.

```
src/features/Settings/search/
  index.tsx           SettingHeader + the form
  api.ts              GET/PUT/DELETE, and the response types
  formState.ts        form values ⇄ UserSearchOverrides (pure, no React)
  features/SearchForm.tsx
```

Everything 1.7 recorded holds here — an unset field is absent from the PUT body,
the inputs seed from `overrides` and never from `effective`, and the pane renders
the response rather than what it sent. Three things are specific to this pane:

- **Trimming has two different outcomes here, and the form has to survive both.**
  An unknown category is *dropped*; an out-of-range `maxCategories` is *clamped*
  to the ten categories that exist. `contract.test.ts` asserts both against the
  real `normalizeSearchOverrides`, which is how the difference was found — the
  first draft of that test assumed the cap was dropped like the category.
- **The stored category list can be longer than the list in force.** It is the
  fan-out order and `maxCategories` keeps the first N, so the pane shows all of
  what the user chose while `effective.categories` shows what actually runs. The
  two are deliberately different numbers on screen.
- **`language` is trimmed client-side** — the only client-side normalization in
  either pane. The server's tag pattern rejects a trailing space and would drop
  the whole field for it, silently.

Upstream edits are 1.7's five registration points and no logic: the

`tiers` and `categories` became `OrderedMultiSelect`; `languages` became

knowing before touching this:

- **`languages` was not merely awkward — it could not be filled in.** base-ui's
  `Select` accepts `mode="tags"` and `tokenSeparators`, but **it never creates a
  value that is not already in `options`**: typing is a typeahead over the option
  list and Enter commits whichever option it landed on. 1.7's field passed no
  options, so there was nothing to commit and no transcript language could be
  set at all. Adding options makes it worse, not better: typing a valid but
  unlisted tag like `sw` (Swahili) commits the nearest highlight, `sv` (Swedish).
  Both language fields are therefore built on base-ui's **`AutoComplete`**, which
  is a real text input with a suggestion list. Anything else in this repo that
  wants free-text tag entry will hit the same wall.
- **The rejection is now visible at the moment of entry.** Both routes validate a
  tag's shape and drop what fails rather than failing the write, which is right —
  `en, klingon` should still get you English — but it meant a typo vanished under
  a "saved" toast. `languageTags.ts` restates the rule so the pane can name what
  it refused and show the canonical spelling that will be stored. Language names
  come from `Intl.DisplayNames` in the reader's own locale, so the suggestions
  need no translated string table and still cover every tag.
- **`languageTags.contract.test.ts` is the drift guard**, the panes' own
  `contract.test.ts` mechanism aimed at a rule that lives in two other files. One
  corpus of 24 inputs goes through `normalizeSearchLanguage`, `normalizeLanguages`
  and this module; if any of the three drifts, it fails. It also pins the one
  deliberate difference between the routes — search canonicalizes case,
  extraction lowercases, because that is what it deduplicates on.

## What CI will and will not tell you

Three things about this repo's CI are worth knowing before you read a red check
on a `packages-lobe` change:

- **The repo-wide install outage is fixed by handing the SDK transport back to
  fetch.** `bun install --frozen-lockfile` could not resolve two
  specifiers #422 (`d81427c7`) introduced in
  `packages/qwksearch-api-client/package.json`, because neither version was
  ever published:

  | Specifier | Latest actually on npm |
  |---|---|
  | `api2client: ^1.0.1` | 1.0.0 |
  | `grab-url: ^1.6.23` | 1.6.22 |

  The install died before compiling a line, so all 24 Coverage jobs, Test
  Reports, Publish to npm, Lockfile and the Cloudflare Workers build went down
  with it, on `master` and on every branch. Reverting #422 is what cleared it:
  `qwksearch-api-client` sends its requests with the generated Hey API fetch
  client again, the package declares no runtime dependencies, and the lockfile
  needed no change — it never carried an entry for those two.

  **Do not re-land the grab transport by downgrading the specifiers**, which is
  the obvious-looking move and does not work: `api2client@1.0.0` is published
  broken — its tarball ships only `README.md`, `package.json` and `src/`, while
  `main`, `module`, `types`, `exports` and `bin` all point into a `dist/` that
  is not in the package, so Vite fails with "Failed to resolve entry for
  package". `^1.6.23` is equally real: it is the first `grab-url` carrying
  `onRawResponse`, which is what puts the HTTP status and the parsed error body
  on a failed result. Without it a failed request resolves with no `response`
  at all and `response.status` throws — the exact status-branching that
  `error-result-shape.test.ts` exists to protect.

  Both packages live outside this repo (`vtempest/GRAB-URL`), so nothing here
  can publish them. Re-landing #422 is a `git revert` of the revert plus a
  `bun install` once `api2client@1.0.1` and `grab-url@1.6.23` are on npm —
  check with `npm view api2client version` before trying.
- **Nothing in CI builds or tests `packages-lobe`.** The root `workspaces` are
  `packages/*`, `packages/render-url-to-html/*` and `apps/*`; `packages-lobe` is
  a separate pnpm workspace outside that graph, so no job installs it. A green
  run says nothing about a change made there, and a red one is almost certainly
  not yours. Your own `bunx vitest run` under `packages-lobe` is the only
  signal — which is why 5.4's "bundle budget in CI" needs a whole new job.
- **The Coverage workflow was already red on `master` before that**, for
  unrelated reasons the install fix did not touch. As of `52eb7cce` (#412, run
  34445607248) and still at `c67266af` (#430, run 34540292102) **four** jobs
  failed with nothing of that work in them: `chat-agent-toolkit`,
  `extract-youtube`, `search-web-api` and `shadcn-settings`. All four are now
  fixed, and none of them was a flake — each was a real defect:

  | Job | What was actually wrong |
  |---|---|
  | `extract-youtube` | `typescript@^7.0.2` is the native compiler and exposes no JS API, so `ts-jest` refused to start and all 10 suites reported 0 tests. The package now aliases `typescript` to `@typescript/typescript6`, which the root already installed but nothing consumed. |
  | `chat-agent-toolkit` | `openrouter-default-model.test.js` asserted a default of `nvidia/nemotron-3-super-120b-a12b:free` and a model `type` of `text-generation`; the database says `openrouter/free` (the auto-router every consumer prefers) and `text`. The assertions were stale, not the data. |
  | `shadcn-settings` | `TextControl` rendered a fully controlled `<input>` with no draft state, so a host passing only `onCommit` — which the optional `onChange` advertises as supported — could not type at all, and blur committed the stale value. |
  | `search-web-api` | Three separate faults: an autocomplete *example* was named `*.test.ts` and Vitest fails a test file that declares no suite; the mocked-fetch dispatcher matched `search.yahoo.com/search` before `news.search.yahoo.com/search`, so `yahoo_news` parsed the general-search page; and four suites call the live engines, whose rate limits decided the job. |

  Live-network suites are now opt-in behind `RUN_LIVE_TESTS=1`
  (`bun run test:live` in `packages/search-web-api`), so what gates CI is the
  mocked `sources-unit.test.ts` that covers the same engines deterministically.
  `search-web-api` was also the only package whose coverage reporters omitted
  `lcov`, which is why its Codecov upload had always logged
  `not_found_files: packages/search-web-api/coverage/lcov.info`.

  base commit before treating a failure as yours, or you will wave through a
